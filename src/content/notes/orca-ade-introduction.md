## 한 줄로 이해하기

Orca는 Codex나 Claude Code 같은 **CLI 코딩 에이전트를 실행하고 관리하는 작업 환경**입니다. 새로운 모델을 제공하는 서비스라기보다, 이미 사용 중인 에이전트와 구독을 연결해 여러 작업을 동시에 돌리고 결과를 검토하기 위한 ADE(Agent Development Environment)에 가깝습니다.

IDE가 사람이 코드를 편집하는 중심 공간이었다면, ADE는 사람과 에이전트가 함께 작업하는 흐름을 중심에 둡니다. Orca에서는 worktree, 터미널, 브라우저, 파일 편집, diff 검토가 한 화면 안에서 이어집니다.

## 왜 이런 도구가 필요한가

에이전트를 하나만 쓸 때도 작업은 생각보다 여러 단계로 나뉩니다. 브랜치를 만들고, 터미널을 열고, 에이전트에게 요청하고, 실행 결과를 확인하고, diff를 읽고, 다시 수정 요청을 보냅니다. 독립적인 작업이 여러 개라면 이 흐름이 반복되고, 서로 다른 수정이 같은 작업 폴더를 건드릴 위험도 생깁니다.

Orca의 핵심 아이디어는 작업마다 Git worktree를 분리하는 것입니다. 각 에이전트는 자신의 작업 폴더와 브랜치에서 일하고, 사용자는 결과를 비교한 뒤 필요한 변경만 병합합니다. 같은 요청을 여러 에이전트에게 보내는 것도 가능하지만, 핵심은 에이전트 수를 늘리는 데 있지 않습니다. **서로 다른 시도를 섞지 않고 검토 가능한 상태로 유지하는 것**에 있습니다.

## 주요 기능

### 1. worktree 기반 병렬 작업

Orca는 작업마다 격리된 Git worktree를 만듭니다. 따라서 한 작업에서 실험적인 수정이 진행되는 동안, 다른 작업에서는 버그 수정이나 문서 정리를 계속할 수 있습니다. 같은 프롬프트를 여러 에이전트에 보내 결과를 비교하고, 더 적절한 변경을 선택하는 방식도 지원합니다.

이 기능은 여러 작업이 완전히 독립적일 때 특히 유용합니다. 반대로 같은 파일을 동시에 크게 고치는 작업은 병합 비용이 커질 수 있으므로, 작업 단위를 먼저 나누는 편이 좋습니다.

### 2. 여러 CLI 에이전트 연결

Codex, Claude Code, OpenCode, Gemini, Copilot 등 CLI 형태의 에이전트를 한 환경에서 실행할 수 있습니다. Orca가 모델 사용권을 대신 제공하는 구조는 아닙니다. 기존 로그인 상태와 구독을 연결하는 방식이므로, 어떤 에이전트를 쓸지와 각 에이전트의 사용량 관리는 여전히 사용자의 선택입니다.

여기서 중요한 점은 “어떤 모델이 더 좋은가”보다 역할을 어떻게 나눌지입니다. 예를 들어 한 에이전트에는 구현을, 다른 에이전트에는 테스트 보강이나 diff 검토를 맡길 수 있습니다.

### 3. 터미널·파일·브라우저를 작업 문맥에 연결

작업별 터미널을 나눠 열고, 파일을 편집하며, 브라우저에서 결과를 확인할 수 있습니다. 터미널은 분할 화면과 스크롤백 검색을 제공하고, 작업 공간 안에서 Markdown·이미지·PDF·저장소 문서도 미리 볼 수 있습니다.

특히 화면 문제를 다룰 때는 Design Mode가 눈에 띕니다. worktree마다 Chromium 창을 열고, 페이지의 요소를 클릭해 해당 HTML·CSS·잘라낸 스크린샷을 에이전트에게 전달할 수 있습니다. “버튼이 이상하다”처럼 모호한 요청보다, 실제 요소와 화면 근거를 함께 주는 방식입니다.

### 4. diff 검토와 협업 흐름

에이전트가 만든 변경은 결국 사람이 검토해야 합니다. Orca는 diff 줄에 Markdown 주석을 달고, 여러 의견을 모아 에이전트에게 다시 보낼 수 있습니다. GitHub의 PR·이슈·프로젝트 보드, Linear 이슈도 앱 안에서 다룰 수 있어 작업 문맥을 옮겨 다니는 횟수를 줄이는 데 초점을 둡니다.

이 흐름은 에이전트가 만든 코드를 자동으로 신뢰하기 위한 장치가 아닙니다. 오히려 **검토와 피드백을 반복하기 쉽게 만드는 장치**로 보는 편이 맞습니다.

### 5. 원격 worktree와 사용량 확인

성능이 더 좋은 원격 컴퓨터에서 에이전트를 실행하고 싶다면 SSH worktree를 연결할 수 있습니다. 공식 소개에 따르면 파일 편집·Git·터미널을 원격 환경에서 다루고, 재연결·포트 포워딩·패스프레이즈 캐싱을 지원합니다.

모바일 동반 앱에서는 진행 중인 에이전트 상태와 Codex·Claude 사용량을 확인하고, 자리를 비운 동안에도 작업을 이어갈 수 있습니다. 이는 코드 작성 기능이라기보다 병렬 작업의 상태를 놓치지 않기 위한 관리 기능에 가깝습니다.

## 처음 써 볼 때의 작은 실험

처음부터 여러 에이전트에 큰 기능을 맡기기보다, 같은 작은 버그를 두 개의 worktree에서 해결해 보는 편이 좋습니다.

1. 재현 가능한 버그 하나와 통과 기준을 적습니다.
2. 첫 worktree에는 구현을, 두 번째 worktree에는 원인 분석과 테스트 보강을 요청합니다.
3. 각 작업의 diff와 테스트 결과를 비교합니다.
4. 더 적은 변경으로 기준을 만족한 결과를 골라 병합합니다.

이 실험에서 확인할 질문은 단순합니다. “에이전트를 하나 더 늘렸을 때, 결과의 품질이 좋아졌는가? 아니면 검토할 변경만 늘어났는가?”입니다. 이 답이 정리되면 Orca를 계속 쓸 이유도 훨씬 분명해집니다.

## 기억할 점

Git worktree는 작업 충돌을 줄이는 도구이지, 권한을 제한하는 보안 sandbox가 아닙니다. 에이전트가 실행하는 명령과 접근 권한은 여전히 점검해야 합니다. 또한 병렬 실행은 요청 수·사용량·검토량을 함께 늘릴 수 있으므로, 독립적인 작업부터 시작하는 것이 안전합니다.

Orca는 “에이전트가 알아서 개발해 주는 IDE”라기보다, 여러 에이전트의 작업을 분리하고 근거를 모아 사람이 선택하기 쉽게 만드는 관제 화면에 가깝습니다. Codex나 Claude Code를 이미 쓰고 있고, 독립적인 작업을 병렬로 운영해야 할 때 가장 의미가 큽니다.
